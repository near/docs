A non-fungible token contract associates each token ID with an owner. Transfers, approvals, and callbacks must preserve that ownership even when another contract fails or changes state before a callback executes.

Start with the [Rust NFT reference implementation](https://github.com/near-examples/NFT). It uses `near-contract-standards` for the core NFT interface, metadata, enumeration, and approvals. Use this guide to understand the guarantees those components provide before adding your own behavior.

For minting and interacting with an existing contract, see [Using NFTs](/primitives/nft/nft). The [NFT standards](/primitives/nft/standard) describe the interfaces and optional extensions.

## Ownership and minting

A token ID must be unique within its NFT contract, and each existing token must have one owner. Identify an NFT by both its contract account and token ID: different contracts can use the same ID.

Minting rules are application decisions. The reference example allows only its configured contract owner to mint. If you add public minting, supply limits, or payments, define and test those rules explicitly. Minting must keep ownership, metadata, and any enumeration indexes consistent.

Metadata describes a token; it does not authorize transfers. Define who can change metadata and what buyers can expect to remain stable, including any externally hosted media.

## Storage and deposits

Minting tokens and adding approvals increase contract storage. The reference implementation charges attached NEAR for that storage and refunds excess deposits. Changes to metadata or custom collections can change the storage required.

NFT storage accounting differs from the FT registration workflow. Follow the NFT implementation's storage measurements rather than copying a fixed FT registration deposit.

Transfers and approval revocations require [exactly 1 yoctoNEAR](/smart-contracts/security/one_yocto). Approvals need a deposit that covers the additional storage. These deposits are separate from any price your application charges for a token.

## Transfers and approvals

Under [NEP-171](https://github.com/near/NEPs/blob/master/neps/nep-0171.md), only the owner or an authorized approved account may transfer a token. A successful transfer clears the previous owner's approvals.

[NEP-178 approvals](https://github.com/near/NEPs/blob/master/neps/nep-0178.md) authorize another account, such as a marketplace, to transfer a specific token. Each approval has an ID. A marketplace should record that ID when listing and supply it when transferring, so an old listing cannot use a later approval.

Approving a marketplace does not transfer ownership. If its `nft_on_approve` callback fails, the approval itself can still remain in place; check the token's approval state rather than inferring it from the callback outcome.

## Transfer callbacks

`nft_transfer_call` transfers ownership to the receiver, calls `nft_on_transfer`, and then resolves the result. The receiver returns `false` to keep the NFT or `true` to request its return. A failed receiver call also requests a return through the resolver.

The resolver must be private and must check current ownership before returning the token. If the receiver has already transferred it onward, the resolver must not take it from the new owner. When receiving NFTs, verify that the predecessor is an NFT contract your application accepts.

These calls execute across separate receipts. Test the final owner and approval state after resolution, including when the receiver changes state before returning.

## Royalties and marketplaces

The reference NFT example does not implement royalties. If you add them, [NEP-199](https://github.com/near/NEPs/blob/master/neps/nep-0199.md) defines a payout interface for marketplaces to use.

A payout response describes who should receive funds; the marketplace performs the payments. It must validate the number of recipients, prevent arithmetic overflow, and ensure the amounts do not exceed the available balance. Returning a payout map does not itself pay royalties or make every transfer enforce them.

## Test the guarantees

Run the reference repository's tests before making changes. Its [core](https://github.com/near-examples/NFT/blob/master/tests/tests/core.rs), [approval](https://github.com/near-examples/NFT/blob/master/tests/tests/approval.rs), and [enumeration](https://github.com/near-examples/NFT/blob/master/tests/tests/enumeration.rs) tests exercise the standard behavior. Extend them for your minting rules and any added features.

| Scenario | What to assert |
| --- | --- |
| Minting | Duplicate IDs and unauthorized minting fail; ownership and enumeration remain consistent. |
| Storage | Insufficient deposits fail; excess deposits and released approval storage are refunded correctly. |
| Transfer | Unauthorized callers fail; successful transfers update ownership and clear old approvals. |
| Revoke and reapprove | A stale approval ID cannot authorize a transfer. |
| Receiver accepts, rejects, or panics | The final owner and approval state match the resolver's outcome. |
| Receiver transfers onward | The resolver preserves the new owner's token. |
| Optional royalty extension | Payouts respect recipient limits and the available balance, including rounding. |

Use [unit tests](/smart-contracts/testing/unit-test) for permission and state checks and [integration tests](/smart-contracts/testing/integration-test) for receiver calls and callbacks. Inspect receipt outcomes alongside final state; a successful transaction alone does not establish that every receipt succeeded.
