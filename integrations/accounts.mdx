NEAR supports implicit accounts with 64-character hexadecimal IDs derived locally from an ED25519 public key. An account can be created with no initial deposit; the creator pays a **0.007 NEAR** creation charge through gas fees, plus the other transaction fees.

<Tip>
See the [NEAR account model](/protocol/accounts-contracts/account-model) for account types, access keys, and permissions.
</Tip>

---

## Implicit Accounts {#implicit-accounts}

An ED25519 implicit account ID is the 64-character lowercase hexadecimal encoding of its 32-byte public key. Exchanges can derive deposit addresses locally before creating the accounts on-chain. The corresponding private key signs transactions after account creation.

<Info>
Specification: [NEAR implicit accounts](https://nomicon.io/DataStructures/Account.html#near-implicit-account-id).
</Info>

### Generate a key pair and account ID {#creating-an-account-locally}

The CLI generates an ED25519 key pair and saves the credentials to `~/.near-credentials/implicit`. The account ID is derived locally; this command does not create the account on-chain.

```bash
# Test environment should use the testnet, for production use mainnet
export NEAR_ENV=testnet

near account create-account fund-later use-auto-generation save-to-folder ~/.near-credentials/implicit
```

Example output:
```
The file "~/.near-credentials/implicit/8bca86065be487de45e795b2c3154fe834d53ffa07e0a44f29e76a2a5f075df8.json" was saved successfully

Here is your console command if you need to script it or re-run:
    near account create-account fund-later use-auto-generation save-to-folder ~/.near-credentials/implicit
```

### Create the account on-chain {#transferring-to-the-implicit-account}

Deriving an address locally does not create the account on-chain. Before the account can send transactions, including [meta-transactions](/web3-apps/tutorials/meta-transactions), it must be created on-chain and its creation charge paid.

The **first transfer to the address creates the account**, including a transfer of **0 NEAR**. The sender pays the **0.007 NEAR** creation charge through gas fees, plus other transaction fees. See [account creation costs](#account-creation-cost).

Example: create `0861ea8ddd696525696ccf3148dd706c4fda981c64d8a597490472594400c223` with a zero-deposit transfer:

```bash
near tokens <your_account_id> send-near 0861ea8ddd696525696ccf3148dd706c4fda981c64d8a597490472594400c223 '0 NEAR' network-config testnet sign-with-keychain send
```

### Transfer from an implicit account {#using-the-implicit-account}

After the account is created and funded, submit a transfer using its saved access-key file:

```bash
export ACCOUNT="8bca86065be487de45e795b2c3154fe834d53ffa07e0a44f29e76a2a5f075df8"

near tokens $ACCOUNT send-near <receiver> '<amount> NEAR' network-config testnet sign-with-keychain send
```

<Tip>
The `near-cli` allows you to use keys from multiple sources, including the keychain, local files, ledger, or a private key directly.
</Tip>

### Derive the account ID from a public key {#bonus-converting-public-key-using-python-for-learning-purposes}

Requires Python 3 and the `base58` package.

```bash
# Install the package
pip3 install --user base58

# Start the Python interpreter
python3
```

Set `pk58` to the Base58-encoded public key, excluding the `ed25519:` prefix:

```python
import base58

pk58 = 'BGCCDDHfysuuVnaNVtEhhqeT4k9Muyem3Kpgq2U1m9HX'
base58.b58decode(pk58).hex()
```

Output:
```
'98793cd91a3f870fb126f66285808c7e094afcfc4eda8a970f6648cdf0dbd6de'
```

This separate public-key example produces a different account ID from the generated account above. Applying the same conversion to that generated account’s public key reproduces its account ID.

## Key management and recovery {#improper-key-management}

Backup keys can provide signing authority if another key is lost or deleted. Recovery depends on the access keys and contract permissions that remain available.

### Loss of `FullAccess` key

Loss of the only `FullAccess` private key removes the ability to sign transactions with that key.
Recovery depends on any remaining authorized contract methods or recovery authority. If no usable signing authority or contract recovery path remains, the funds can become inaccessible.

### Loss of `FunctionCall` access key

Deleting a `FunctionCall` access key revokes its on-chain permissions even if its secret still exists locally; losing a local secret does not remove the on-chain key. A function-call key alone does not ordinarily authorize native transfers or key replacement.
Recovery depends on any remaining authorized contract methods or recovery authority. If no usable signing authority or contract recovery path remains, the funds can become inaccessible.

## Frequently Asked Questions

<AccordionGroup>

<Accordion title="How are addresses generated?" id="how-are-addresses-generated%3F">

Please check out the spec here on accounts https://nomicon.io/DataStructures/Account.html.

</Accordion>

<Accordion title="What is the balance record-keeping model on the NEAR platform?" id="what-is-the-balance-record-keeping-model-on-the-near-platform%3F">

NEAR uses an `Account`-based model. All users and contracts are associated with at least 1 account. Each account lives on a single shard. Each account can have multiple keys for signing transactions.

_You can read [more about NEAR accounts here](https://nomicon.io/DataStructures/Account.html)_

</Accordion>

<Accordion title="How are user accounts represented on-chain?" id="how-are-user-accounts-represented-on-chain%3F">

Users create accounts with human-readable names (eg `alice`) which can contain multiple keypairs with individual permissions. Accounts can be atomically and securely transferred between parties as a native transaction on the network. Permissions are programmable with smart contracts as well. For example, a lock up contract is just an account with permission on the key that does not allow to transfer funds greater than those unlocked.

</Accordion>

<Accordion title="How much does account creation cost?" id="account-creation-cost">

Account creation has a **0.007 NEAR** creation charge, collected through **gas fees**.

NEAR supports **zero-balance accounts**: an account can be created with an [initial deposit of 0 NEAR](https://testnet.nearblocks.io/txns/5bkXWTL159ZLMZurFHQGPefYYXmgTH3dZz6J8ihbQoWq/execution), while the creator still pays the creation charge and transaction fees.

</Accordion>

<Accordion title="Is there a minimum account balance?" id="is-there-a-minimum-account-balance%3F">

Accounts pay for their own stored data. For accounts using **770 bytes or less**, the creation charge covers this storage, so no additional storage balance is required.

Accounts using **more than 770 bytes** must reserve a balance to cover **all** their stored data, including the first 770 bytes, at **10^19 yoctoNEAR (0.00001 NEAR) per byte**. Query the current price using [`protocol_config`](/api/rpc/protocol#protocol-config); see [storage staking](/protocol/storage/storage-staking).

Deleting stored data reduces the storage requirement, making any balance no longer needed for storage available.

Creation charges and transaction gas are separate from the balance retained for storage; see [account creation costs](#account-creation-cost).

An account can remain active with a zero balance if it meets the storage requirements above. Explicit deletion removes its native account state. Recreating the account starts with fresh state.

</Accordion>

<Accordion title="How many keys are used?" id="how-many-keys-are-used%3F">

An account can have arbitrarily many keys, as long as it has enough tokens for their storage.

</Accordion>

<Accordion title="How are cryptographic functions used?" id="how-are-cryptographic-functions-used%3F">

Account keys support `ed25519`, `secp256k1`, and `ML-DSA-65`, with different encodings and signing rules. The [transaction examples](/integrations/create-transactions) use ED25519. Consult the [cryptographic definitions for your node version](https://github.com/near/nearcore/tree/2.13.4/core/crypto/src) when implementing other key types.

</Accordion>
