You can send a transfer on NEAR using [NEAR CLI](/tools/cli) or an API library such as [near-api-js](https://github.com/near/near-api-js), [near-kit](https://github.com/r-near/near-kit), or [near-api-rs](https://github.com/near/near-api-rs).

---

## Send a Transfer {#send-a-transfer}

<Tabs>
<Tab title="High-level JS" id="high-level-create-a-transaction">

```js
import { Account, JsonRpcProvider, KeyPairSigner, actions, nearToYocto } from "near-api-js";

const sender = "sender.testnet";
const privateKey = process.env.SENDER_PRIVATE_KEY;
const signer = KeyPairSigner.fromSecretKey(privateKey);

const receiver = "receiver.testnet";

const provider = new JsonRpcProvider({ url: `https://rpc.testnet.near.org` });
const senderAccount = new Account(sender, provider, signer);

const result = await senderAccount.signAndSendTransaction({
  receiverId: receiver,
  actions: [actions.transfer(nearToYocto("1.5"))],
  waitUntil: "FINAL",
});
console.log(result);
```

</Tab>
<Tab title="Low-level JS" id="low-level-create-a-transaction">

```js
import { Account, JsonRpcProvider, KeyPairSigner, actions, nearToYocto } from "near-api-js";

const sender = "sender.testnet";
const privateKey = process.env.SENDER_PRIVATE_KEY;
const signer = KeyPairSigner.fromSecretKey(privateKey);

const receiver = "receiver.testnet";

const provider = new JsonRpcProvider({ url: `https://rpc.testnet.near.org` });
const senderAccount = new Account(sender, provider, signer);

const transaction = await senderAccount.createTransaction({
  receiverId: receiver,
  actions: [actions.transfer(nearToYocto("1.5"))],
  publicKey: await signer.getPublicKey(),
});
const { signedTransaction } = await signer.signTransaction(transaction);

const result = await provider.sendTransactionUntil(signedTransaction, "FINAL");
console.log(result);
```

</Tab>

near tokens <sender_account_id> send-near <receiver_account_id> '1.5 NEAR' network-config testnet sign-with-keychain send

## Concurrent Transactions {#concurrent-transactions}

If you start sending multiple transactions from a same account - e.g. when creating a relayer - you need to manage nonces carefully to avoid conflicts.

In NEAR, accounts can have multiple keys, each with its own nonce sequence. So the simplest way to avoid `nonce` collisions is to use multiple access keys for concurrent transactions.

In `near-api-js` the [`MultiKeySigner`](https://near.github.io/near-api-js/classes/signers_multikey_signer.MultiKeySigner.html) rotates through a set of keys when creating transactions:

```js
import { MultiKeySigner } from "near-api-js";

const secretKeys = [
  process.env.SENDER_PRIVATE_KEY,
  process.env.SENDER_PRIVATE_KEY_2,
];
const multiKeySigner = MultiKeySigner.fromSecretKeys(secretKeys);
const concurrentAccount = new Account(sender, provider, multiKeySigner);

const receivers = [
  "receiver.testnet",
  "receiver-2.testnet",
  "receiver-3.testnet",
  "receiver-4.testnet",
  "receiver-5.testnet",
];

const transfers = [];
for (const receiverId of receivers) {
  transfers.push(concurrentAccount.signAndSendTransaction({
    receiverId,
    actions: [actions.transfer(nearToYocto("1.5"))],
    waitUntil: "FINAL",
    retries: 0,
  }));
}
const results = await Promise.allSettled(transfers);
console.log(results);
```

## Submission errors and retries

With `near-api-js` 7.3.1, error handling depends on the method used:

| Method | Error behavior |
| --- | --- |
| `Account.signAndSendTransaction()` | Throws RPC errors and, by default (`throwOnFailure: true`), execution failures. Set `throwOnFailure: false` to inspect execution failures in the returned `result.status`; RPC errors still throw. |
| `provider.sendTransactionUntil()` or `provider.sendJsonRpc("send_tx", …)` | Throws RPC errors, but returns execution failures in `result.status.Failure`. Check both `final_execution_status` and `status` before settling the withdrawal. |
| `Promise.allSettled()` in the concurrent example | Preserves each call's fulfilled result or rejected error in input order. Inspect every entry independently. |

Typed errors are exported from `near-api-js/rpc-errors`. When the high-level method throws a transaction or contract execution error derived from a submitted transaction, its `transactionResult` contains the RPC response, including receipt outcomes. Use that response to inspect `status.Failure` and the failed receipt; read-only call errors do not include transaction outcomes.

`Account.signAndSendTransaction()` defaults to up to 10 retries after `InvalidNonceError`, constructing and signing a new transaction on each retry. These examples set `retries: 0` so withdrawal recovery controls replacement transactions. This setting does not disable the provider's HTTP retries.

Before broadcasting a withdrawal, persist its business intent, network, signer, reserved nonce, signed bytes, and transaction hash. Keep one recovery process in control of that intent until its outcome is resolved.

| Result | Handling |
| --- | --- |
| Explicit validation rejection | Correct the reported key, permissions, balance, nonce, or block hash. If this intent was submitted previously, resolve that earlier hash before creating a replacement. |
| Timeout, connection loss, server error, or unknown transaction | Submission is uncertain. Query the saved hash and signer on the same network, using another provider or an archival node when needed. Do not assume the withdrawal failed. |
| Included or still executing | Poll [`tx` or `EXPERIMENTAL_tx_status`](/api/rpc/transactions#transaction-status-with-receipts) with `wait_until: "FINAL"`; require `final_execution_status === "FINAL"` before settlement. |
| Finalized execution failure | Inspect the failed receipt and its `ActionError.index`, where present. Account for fees and refunds, and reconcile any earlier successful receipts before retrying the business operation. |

If rebroadcasting is necessary, resend **the same signed bytes** while their reference block remains valid. A newly signed transaction has a different hash and can execute a second payment. An expired block hash or consumed nonce on a later attempt does not prove that the original transaction never executed. Resolve the original outcome and reconcile balances before issuing a replacement under the same intent lock.

Actions within one receipt are atomic; separate receipts are not rolled back together. A contract call can fail after an earlier receipt has transferred funds. Keep transport errors, validation rejections, and execution failures distinct in your withdrawal records.

## Frequently Asked Questions

<Accordion title="What is the fee structure for on-chain transactions?" id="what-is-the-fee-structure-for-on-chain-transactions%3F">

NEAR uses a gas-based model where prices are generally deterministically adjusted based on congestion of the network.

We avoid making changes that are too large through re-sharding by changing number of available shards (and thus throughput).

Accounts don’t have associated resources. Gas amount is predetermined for all transactions except function calls. For function call transactions the user (or more likely the developer) attaches the required amount of gas. Unused prepaid gas is refunded according to current runtime rules, including any configured unused-gas refund penalty. Query the runtime configuration and budget gas for the contract being called.

</Accordion>

<Accordion title="How do we know how much gas to add to a transaction?" id="how-do-we-know-how-much-gas-to-add-to-a-transaction%3F">

- See [Gas fees](/protocol/transactions/gas).
- See API documentation for [discovering gas price via RPC here](/api/rpc/gas#gas-price).

The issuer of a transaction should attach some amount of gas by taking a guess at budget which will get the transaction processed. The contract knows how much to fund different cross contract calls. Gas price is calculated and fixed per block, but may change from block to block depending on how full / busy the block is. If blocks become more than half full then gas price increases.

See [gas purchase, burn, and refund accounting](/protocol/transactions/gas) for the current fee model.

</Accordion>
