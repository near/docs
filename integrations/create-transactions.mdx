To construct & process transactions you can use one of our API libraries, such as [`near-api-js`](/tools/near-api). There are many ways to create transactions but for this example we'll show you two ways to create a simple token transfer transaction.

- [HIGH LEVEL](#high-level-create-a-transaction) - _easiest way to create a transaction_
- [LOW LEVEL](#low-level-create-a-transaction) - _performs the exact same transaction as above, but deconstructs the entire process for those curious about each step_

At the core, all transactions require the following:

- `signerId` _(account ID of the transaction originator)_
- `signerPublicKey`
- `receiverId` _(account ID of the transaction recipient)_
- `nonceForPublicKey` _(a unique increasing nonce for the selected access key)_
- `actions` _( [[click here]](/protocol/transactions/transaction-anatomy#actions) for supported arguments)_
- `blockHash` _(a recent block hash (within the configured block-based validity period) to prove the transaction was recently created)_

See [Transaction Class](https://github.com/near/near-api-js/blob/2546c85354ab888dc1f559b0e54cfac51f03b484/src/transactions/schema.ts) for a more in depth outline.

## The life of a transaction: {#the-life-of-a-transaction}

<Steps>
  <Step title="Create and sign">

    A client creates a transaction, computes the transaction hash and signs this hash to get a signed transaction. Now this signed transaction can be sent to a node.

  </Step>

  <Step title="Route to the signer’s shard">

    The RPC interface receives the transaction and routes it to the correct physical node using `signer_id`.  Since the `signer_id` must be a NEAR Account ID which lives on a single shard, the account is mapped to a shard which is followed by at least one validator running at least one machine with an IP address.

  </Step>

  <Step title="Validate and propagate">

    When a node receives a new signed transaction, it validates the transaction for signer, receiver, account balance, cost overflow, signature, etc. ([see here](https://nomicon.io/RuntimeSpec/Scenarios/FinancialTransaction.html#transaction-to-receipt)) and gossips it to all peers following the same shard. If a transaction has an invalid signature or would be invalid on the latest state, it is rejected quickly and returns an error to the original RPC call.

  </Step>

  <Step title="Add to the transaction pool">

    Valid transactions are added to the transaction pool (every validating node has its own independent copy of a transaction pool). The transaction pool maintains transactions that are not yet discarded and not yet included into the chain.

  </Step>

  <Step title="Select transactions for a chunk">

    A pool iterator is used to pick transactions from the pool one at a time, with increasing nonces for each access key (there is no global ordering across accounts), until the pool is drained or some chunk limit is reached (max number of transactions per chunk or max gas burnt per chunk to process transactions).  Please refer to articles on the [pool iterator](https://nomicon.io/ChainSpec/Transactions.html?highlight=pool#pool-iterator) and [gas](/protocol/transactions/gas) for more details.

    Transactions that cannot fit in the current chunk can remain pending. Admission to a node’s pool does not guarantee inclusion or execution; do not use pool admission as a settlement signal.

  </Step>

  <Step title="Validate before chunk production">

    Before producing a chunk, transactions are ordered and validated again. This is done to produce chunks with only valid transactions across a distributed system.

  </Step>

  <Step title="Read execution outcomes">

    Execution errors are recorded in transaction and receipt outcomes. Read these outcomes through RPC; a successful HTTP response or initial transaction outcome does not prove that later receipts succeeded.

  </Step>
</Steps>

## Submission errors and retries

Before broadcasting a withdrawal, persist its business intent, network, signer, reserved nonce, signed bytes, and transaction hash. Keep one recovery process in control of that intent until its outcome is resolved.

| Result | Handling |
| --- | --- |
| Explicit validation rejection | Correct the reported key, permissions, balance, nonce, or block hash. If this intent was submitted previously, resolve that earlier hash before creating a replacement. |
| Timeout, connection loss, server error, or unknown transaction | Submission is uncertain. Query the saved hash and signer on the same network, using another provider or an archival node when needed. Do not assume the withdrawal failed. |
| Included or still executing | Poll [`tx` or `EXPERIMENTAL_tx_status`](/api/rpc/transactions#transaction-status-with-receipts) with `wait_until: "FINAL"`; require `final_execution_status === "FINAL"` before settlement. |
| Finalized execution failure | Inspect the failed receipt and its `ActionError.index`, where present. Account for fees and refunds, and reconcile any earlier successful receipts before retrying the business operation. |

If rebroadcasting is necessary, resend **the same signed bytes** while their reference block remains valid. A newly signed transaction has a different hash and can execute a second payment. An expired block hash or consumed nonce on a later attempt does not prove that the original transaction never executed. Resolve the original outcome and reconcile balances before issuing a replacement under the same intent lock.

Actions within one receipt are atomic; separate receipts are not rolled back together. A contract call can fail after an earlier receipt has transferred funds. Keep transport errors, validation rejections, and execution failures distinct in your withdrawal records.

## Send a Transfer

### Setup

Use Node.js 24.11 or later and install the SDK version used in these examples:

```bash
npm install near-api-js@7.3.1
```

Use a funded testnet account with an ED25519 [full-access key](/protocol/accounts-contracts/access-keys#full-access-keys). Put its secret key in a local `.env` file as `SENDER_PRIVATE_KEY=ed25519:...` and keep that file out of source control. Set `sender` and `receiver` in the selected script to your testnet accounts.

Both examples send 1.5 testnet NEAR. Run one example at a time with the selected access key. `nearToYocto()` converts the decimal amount to an integer in yoctoNEAR without floating-point rounding.

### High-level transaction {#high-level-create-a-transaction}

`Account.signAndSendTransaction()` constructs, signs, and sends the transfer. Save this as `send-tokens-easy.mjs`:

```js
import { Account, JsonRpcProvider, KeyPairSigner, actions, nearToYocto } from "near-api-js";

const sender = "sender.testnet";
const receiver = "receiver.testnet";
const networkId = "testnet";

const amount = nearToYocto("1.5");

const privateKey = process.env.SENDER_PRIVATE_KEY;
if (!privateKey?.startsWith("ed25519:")) {
  throw new Error("Set SENDER_PRIVATE_KEY to the test account's ED25519 secret key");
}
const signer = KeyPairSigner.fromSecretKey(privateKey);

const provider = new JsonRpcProvider({ url: `https://rpc.${networkId}.near.org` });
if (await provider.getNetworkId() !== networkId) throw new Error("Wrong network");
const senderAccount = new Account(sender, provider, signer);

const result = await senderAccount.signAndSendTransaction({
  receiverId: receiver,
  actions: [actions.transfer(amount)],
  waitUntil: "FINAL",
  retries: 0,
});
console.log(result);
```

```bash
node --env-file=.env send-tokens-easy.mjs
```

This constructs, signs, and sends the transfer, and throws if execution fails. `retries: 0` disables automatic re-signing after a nonce error. Inspect the returned result or open its transaction hash in [NearBlocks Explorer](https://testnet.nearblocks.io/). This convenience method is a demonstration. For production withdrawals, use the low-level workflow to persist signed bytes and the hash before submitting. After a timeout, reconcile that hash before signing a replacement.

### Low-level transaction {#low-level-create-a-transaction}

This workflow explicitly obtains the nonce and recent block hash, constructs the transaction, and signs its serialized hash before submission. Save this as `send-tokens-deconstructed.mjs`:

```js
import {
  JsonRpcProvider, KeyPair, nearToYocto, actions as transactionActions,
  createTransaction, encodeTransaction, SignedTransaction, Signature, baseDecode
} from "near-api-js";
import { createHash } from "node:crypto";

const sender = "sender.testnet";
const receiver = "receiver.testnet";
const networkId = "testnet";

const amount = nearToYocto("1.5");

const provider = new JsonRpcProvider({
  url: `https://rpc.${networkId}.near.org`
});
if (await provider.getNetworkId() !== networkId) throw new Error("Wrong network");

const privateKey = process.env.SENDER_PRIVATE_KEY;
if (!privateKey?.startsWith("ed25519:")) {
  throw new Error("Set SENDER_PRIVATE_KEY to the test account's ED25519 secret key");
}
const keyPair = KeyPair.fromString(privateKey);

const publicKey = keyPair.getPublicKey();

const accessKey = await provider.viewAccessKey({
  accountId: sender,
  publicKey,
  finalityQuery: { finality: "final" },
});
if (accessKey.permission !== "FullAccess") throw new Error("Full-access key required");
if (accessKey.nonce > BigInt(Number.MAX_SAFE_INTEGER)) {
  throw new Error("Use an RPC decoder that preserves large integer nonces");
}

const nonce = accessKey.nonce + 1n;

const actions = [transactionActions.transfer(amount)];

const block = await provider.viewBlock({ finality: "final" });
const recentBlockHash = baseDecode(block.header.hash);

const transaction = createTransaction(
  sender,
  publicKey,
  receiver,
  nonce,
  actions,
  recentBlockHash
);

const serializedTx = encodeTransaction(transaction);

const serializedTxHash = createHash("sha256").update(serializedTx).digest();

const signature = keyPair.sign(serializedTxHash);

const signedTransaction = new SignedTransaction({
  transaction,
  signature: new Signature({
    keyType: transaction.publicKey.keyType,
    data: signature.signature,
  }),
});

// encodes transaction to serialized Borsh (required for all transactions)
const signedSerializedTx = encodeTransaction(signedTransaction);
// sends the signed transaction and waits for finalized execution
const result = await provider.sendJsonRpc("send_tx", {
  signed_tx_base64: Buffer.from(signedSerializedTx).toString("base64"),
  wait_until: "FINAL",
});
if (result.final_execution_status !== "FINAL") throw new Error("Execution is not final");
console.log(result);
```

```bash
node --env-file=.env send-tokens-deconstructed.mjs
```

For production, reserve nonces in a persistent allocator shared by every worker using the same sender/key. Include signed and submitted transactions that have not finalized, keep nonces as integer-safe values, and synchronize with on-chain state during recovery. An SDK instance’s local nonce cache does not coordinate independent processes. Ordinary nonces must increase; strict modes and gas-key lanes have different rules, so these examples use ordinary ED25519 keys only.

Before production submission, persist the business intent, network identity, original sender, exact signed bytes, and transaction hash (`baseEncode(serializedTxHash)`) atomically with your reserved balance/nonce. Import `baseEncode` from `near-api-js` when deriving this hash. If submission times out, query that hash and sender with `wait_until: "FINAL"`; resend only the identical saved bytes while valid. A new nonce or block hash creates a different transaction. See [submission recovery](/integrations/create-transactions#submission-errors-and-retries).

## Frequently Asked Questions

<AccordionGroup>

<Accordion title="What is the fee structure for on-chain transactions?" id="what-is-the-fee-structure-for-on-chain-transactions%3F">

NEAR uses a gas-based model where prices are generally deterministically adjusted based on congestion of the network.

We avoid making changes that are too large through re-sharding by changing number of available shards (and thus throughput).

Accounts don’t have associated resources. Gas amount is predetermined for all transactions except function calls. For function call transactions the user (or more likely the developer) attaches the required amount of gas. Unused prepaid gas is refunded according to current runtime rules, including any configured unused-gas refund penalty. Query the runtime configuration and budget gas for the contract being called.

</Accordion>

<Accordion title="How do we know how much gas to add to a transaction?" id="how-do-we-know-how-much-gas-to-add-to-a-transaction%3F">

- See reference documentation here: https://nomicon.io/Economics/Economics.html
- See API documentation for [discovering gas price via RPC here](/api/rpc/gas#gas-price).

The issuer of a transaction should attach some amount of gas by taking a guess at budget which will get the transaction processed. The contract knows how much to fund different cross contract calls. Gas price is calculated and fixed per block, but may change from block to block depending on how full / busy the block is. If blocks become more than half full then gas price increases.

See [gas purchase, burn, and refund accounting](/protocol/transactions/gas) for the current fee model.

</Accordion>

<Accordion title="How do we follow Tx status?" id="how-do-we-follow-tx-status%3F">

See related [RPC interface for fetching transaction status here](/api/rpc/transactions#transaction-status).

</Accordion>

<Accordion title="How are transactions constructed and signed?" id="how-are-transactions-constructed-and-signed%3F">

Transactions are a collection of related data that is composed and cryptographically signed by the sender using their private key. The related public key is part of the transaction and used for signature verification. Only signed transactions may be sent to the network for processing.

Transactions can be constructed and signed offline. Signing itself does not require a node, but the mandatory recent block hash and access-key nonce must be obtained beforehand. Use a fresh finalized block and a nonce reserved for that key; see [transaction construction](/integrations/create-transactions).

See [transactions](/protocol/transactions) in the concepts section of our documentation.

</Accordion>

<Accordion title="How is the hash preimage generated? Which fields does the raw transaction consist of?" id="how-is-the-hash-preimage-generated%3F-which-fields-does-the-raw-transaction-consist-of%3F">

For a transaction, we sign the hash of the transaction. More specifically, what is signed is the `sha256` of the transaction object serialized in borsh (https://github.com/near/borsh).

</Accordion>

<Accordion title="How do transactions work on the NEAR platform?" id="how-do-transactions-work-on-the-near-platform%3F">

A `Transaction` is made up of one or more `Action`s. Common action types include `CreateAccount`,
`DeployContract`, `FunctionCall`, `Transfer`, `Stake`, `AddKey`, `DeleteKey` and `DeleteAccount`. Delegation, global-contract, deterministic-initialization, and gas-key actions are also supported; consult the [versioned action definitions](https://github.com/near/nearcore/blob/2.13.4/core/primitives/src/action/mod.rs). Transactions are composed by a sender and then signed using the private keys of a valid NEAR account to create a `SignedTransaction`. This signed transaction is considered ready to send to the network for processing.

Transactions are received via our JSON-RPC endpoint and routed to the shard where the `sender` account lives. This "home shard" for the sender account is then responsible for processing the transaction and generating related receipts to be applied across the network.

Once received by the network, signed transactions are verified (using the embedded public key of the signer) and processed into an initial action receipt containing the transaction’s action list; function calls can generate additional receipts. Receipts are of two types: `Action Receipt` is the most common and represents almost all actions on the network while `Data Receipt` handles the very special case of "a `FunctionCallAction` which includes a Promise". These receipts are then propagated and applied across the network according to the "home shard" rule for all affected receiver accounts.

These receipts are then propagated around the network using the receiver account's "home shard" since each account lives on one and only one shard. The receiving shard schedules receipt execution subject to dependencies and execution limits.

Receipts may generate other, new receipts which in turn are propagated around the network until all receipts have been applied. If an action fails, state changes within that receipt are rolled back. Earlier successful receipts remain committed, and gas can still be charged. Refunds and callbacks execute as separate receipts; inspect their finalized outcomes.

For more detail, see specs on [`Transactions`](https://nomicon.io/RuntimeSpec/Transactions), [`Actions`](https://nomicon.io/RuntimeSpec/Actions.html), [`Receipts`](https://nomicon.io/RuntimeSpec/Receipts)

</Accordion>

<Accordion title="How does NEAR serialize transactions?" id="how-does-near-serialize-transactions%3F">

We use a simple binary serialization format that's deterministic: https://borsh.io

</Accordion>

<Accordion title="How old can the referenced block hash be before it's invalid?" id="how-old-can-the-referenced-block-hash-be-before-its-invalid%3F">

There is a genesis parameter which can be discovered for any network using:

```sh
http post https://rpc.testnet.near.org jsonrpc=2.0 id=dontcare method=EXPERIMENTAL_genesis_config
# in the line above, testnet may be replaced with mainnet or betanet
```

Use `transaction_validity_period`, measured in blocks, from the [`protocol_config` RPC endpoint](/api/rpc/protocol#protocol-config). For example, `86400` blocks at a 600ms cadence correspond to approximately 14.4 hours; validity is determined by blocks, not a fixed wall-clock deadline.

`epoch_length` specifies the length of an epoch in blocks.

</Accordion>
